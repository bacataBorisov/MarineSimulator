# Project memory

Durable facts and patterns only (not ephemeral session chatter). Prune when obsolete.

- MarineSimulator is a macOS SwiftUI app with a `NavigationSplitView` shell and a map-first dashboard as the primary control surface.
- `NMEASimulator` is the central observable engine/state object; views consume it via SwiftUI environment or `@Bindable`. Do not extract stored properties onto a second observable. Idle and transmit share `performSimulationCycle`; idle still applies full state immediately (console writes now), transmit still publishes value-only at 10 Hz. Do not set `transmitRuntime` on the idle path. Transmit must not copy lat/lon from the 10 Hz input mirror unless `isEditingGPSCoordinates` or `gpsCoordinateSetpointGeneration` changed (map/field teleport). SOG/COG setpoints always copy. Position advances every fast tick with wall dt; do not gate it on the NMEA send interval.
- The engine produces one coherent `SimulationSnapshot` per tick and builds all emitted NMEA sentences from that snapshot.
- While transmitting, the fast 20 Hz scheduler runs on `simulationQueue` (`DispatchSourceTimer`); `TransmitRuntime` owns tick state off the main thread. Main-thread UI is published at 10 Hz via coalesced `DispatchQueue.main.asyncAfter` (latest-wins) — not a `Timer` on `.common`, which fires mid-layout and can freeze MapKit. The NMEA console is an AppKit `NSTextView` that appends/trims lines — do not rebuild it with SwiftUI `ForEach`, and do not mutate the text storage inside `updateNSView`.
- Output is endpoint-based and supports both UDP and TCP; the first endpoint is kept in sync with the top-level IP/port fields. UDP is fire-and-forget: `EHOSTDOWN` / `EHOSTUNREACH` / `ENETDOWN` / `ENETUNREACH` from `sendto` must not paint “The host is down” or stop the tick — `TransportManager` treats those as still sending.
- Settings and live simulator values persist through `UserDefaults`, including layout state, selected panel, sentence intervals, endpoints, presets, live GPS/control values, and the dashboard Live Controls tab (`dashboard.live_control_category`). Docks remount when leaving the dashboard, so that tab must not be `@State`.
- Product direction currently prioritizes external-reader interoperability, manual validation, and protocol fidelity over adding new feature families. Milestone 1 is accepted. Milestone 2 is implemented and not accepted yet (`.agent/guides/m2-polar-dynamics.md`). Instant speed remains the default. A hidden polar override is explicit state, not a boat-profile setting. Clocks stay split: physics 20 Hz, environment and sensor redraw 1 s, NMEA per sentence, UI 10 Hz. `SimulationState` holds `EnvironmentTruth` and `VesselTruth`. While transmitting, the map bearing follows the newest HDT in the console buffer. GNSS and DSC toggles are stored and disabled.
- Configuration follows a basic-first pattern: core setup is always visible, while advanced transport/fault tools are hidden behind an explicit toggle.
- Live weather V1 exists and is provider-backed, not synthetic: it uses Open-Meteo with GPS coordinates and currently overrides true wind and sea-surface temperature only.
- The dashboard map stays full-bleed behind a full-width bottom console; left/right docks sit in the space above the console and shrink as it grows. Console drag uses an AppKit window-space handle (`ConsoleResizeHandle` in `ConsolePanelView`) because SwiftUI `DragGesture` on the moving bar jitters. The handle arms only after pointer movement. The console toolbar's own show/hide button cancels drag and publishes one immediate height. Manual uses a fixed 320-point topics `HStack`, native `List`, and the original console-edge anchors, not `HSplitView`: rapid console resizing otherwise drove split-child min-size updates into an AppKit constraints loop. Keep Manual ephemeral. Parking its scrolled topics list reproducibly traps in SwiftUI `DynamicContainerInfo.tryRemovingItem` with `DynamicPreferenceCombiner`; do not inject an AppKit anchor. A different retention design requires separate review. UserDefaults is persist-only. The dashboard map stays mounted at zero proposed size when leaving the page (updates paused); docks/console remount. Do not destroy `MKMapView` on sidebar changes.
- Connection and Simulation use lazy `retainedForm` stable AppKit hosts. Boat Profile uses lazy `retainedSessionView`: one unchanged root and one `VesselLibrarySession` persist after first visit, preserving selection. Valid Boat Profile edits autosave; invalid intermediate text does not. Keep each retained `NSHostingView` root unchanged; switch activity at the host boundary with normal AppKit layout, inactive `isHidden`, zero size/alpha/hit/accessibility gates, responder resignation/observation, and console-anchor suspend/resume. Do not add synchronous `layoutSubtreeIfNeeded`, recursive per-field mutation, disable automatic `NSWindow` key-view recalculation, or manually own the whole window key loop. The DEBUG no-`isHidden` experiment worsened hitch rate and was removed. Navigation was accepted on 2026-11-12 as visually almost imperceptible with zero heavy destination-body samples; Debug events at or above 33 ms alone are not a failure when runtime correctness and accepted perception hold.
- GPS uses `retainedMapResource` (`GPSSelectorMapResource` in `Views/GPS/MapWithRightClick.swift`): the `GPSConfig` page stays ephemeral, while the `MKMapView` and camera survive sidebar navigation.
- Primary output can be renamed and disabled; the engine no longer forces `outputEndpoints[0].isEnabled = true`.
- The project already has broad engine coverage using the Swift `Testing` framework, including sentence families, persistence, timer/lifecycle, endpoint churn, and fault injection behavior.
- Accepted Debug soak baseline after the freeze fix (dashboard, transmitting): start ~18% CPU / ~410 MB, energy Low. Filter `[MarineSim][hang]`. `CAMetalLayer` 0×0 at launch is known noise. Overnight 16–17 Aug (PID 6805, t≈13.6 h): **17% CPU, 364 MB, energy Low**, beats still ≈7–8. After a 24 h foreground soak, `STALL in=-` with beats at 1 Hz is stacked 1 s compass eases (COG/TWA change at 10 Hz). Keep the 1 s wind/heading ease, but commit a new target at most ~once per 0.85 s unless the step is ≥2.5° (slider). Fold `animationDelta` past 360°. Remount docks+console after sleep, ≥2 min background, or every 15 min on the dashboard. Do not destroy `MKMapView` on that remount.
- Do not put SwiftUI `NSHostingView` inside `MKAnnotationView` — it re-enters MapKit layout and wedges the main thread (100% CPU, HangProbe `STALL`). Boat marker is AppKit `NSImageView` rotation only. Do not call `MKMapView.setCamera` / `addAnnotation` from `makeNSView` or synchronously inside `updateNSView` — defer to the next main-queue turn or launch wedges in `map.update`.

## Engineering conventions (Apple-aligned)

- **Workflow:** Work directly in the parent chat—no subagents, no `/implementer`, no `/verifier`, and no new regression tests unless explicitly requested. Before implementing any step, explain the plan, rationale, and fit with the current architecture and get approval; after implementation and a clean build, the user smoke-tests and verifies the app.
- **Agent shell safety:** All disposable MarineSimulator artifacts belong in the ignored `.agent-scratch/`, never a system temp directory. `/Users/bacataborisov/.local/bin/cursor-clean-marine-scratch` is the only approval-free deletion path and accepts no arguments; `/Users/bacataborisov/.local/bin/cursor-test-marine-boat` owns scratch cleanup, temp environment, DerivedData, result bundle, and the fixed Boat test selection. Invoke either wrapper exactly from the repository root. Safe development commands are narrowly allowlisted in `~/.cursor/permissions.json`; command chaining, pipes, redirects, inline interpreters, arbitrary `python3`/shells, and direct deletion still require approval. `~/.cursor/hooks/guard-scratch-clean.py` fails closed for modified or incorrectly invoked wrappers and approval-gates direct `rm`.
- Prefer **Human Interface Guidelines** and **Swift API Design Guidelines** (check local HIG audit/skill *before* proposing UI changes): clear naming, focused types, layouts and controls that behave like system apps. On macOS 26, anchor short `.popover` alerts tightly to the control cluster with `arrowEdge: .bottom` and `.fixedSize(horizontal: false, vertical: true)` (avoid `.trailing` on narrow single-row popovers, which pinches corners, and back filtered `TextField`s with local `draftText` so rejected chars clear even when underlying `text` stays unchanged).
- **Simplicity, responsiveness, and reliability first:** Repair and build pages with standard SwiftUI controls and explicit `VStack` / `HStack` / `Grid` composition, one observable state owner, and the shared semantic tokens. Reflow from a semantic compact stack to regular/wide columns from available container geometry only when readable controls fit, while preserving reading, keyboard, and accessibility order. A custom `Layout`, cached/type-erased child tree, forced `.id` refresh, delayed invalidation, or new AppKit bridge requires a documented platform failure. Prefer removing failed abstraction layers over keeping compatibility machinery. Add visual effects only after state updates, navigation, resizing, accessibility, and core behavior are reliable.
- **SwiftUI-first:** Implement and evolve the app **visually and structurally in SwiftUI** by default—`View` composition, standard SwiftUI controls (`Slider`, `Picker`, `Button`, materials, stacks), accessibility labels, and platform-appropriate spacing. **Do not** reach for AppKit or `NSViewRepresentable` unless something is **not reasonably achievable** in SwiftUI on the supported macOS baseline, or a **first-party** kit clearly owns the experience (e.g. `MapKit` / `MKMapView`, `MKCompassButton`, `MKZoomControl` on the dashboard map). If an exception is needed, keep the bridge **minimal**, **localized**, and **documented** (comment or PR description).
- Use **`Locale(identifier: "en_US_POSIX")`** (via `NMEANumericFormatting`) for **NMEA numeric fields** so decimal separators stay `.` on all user locales—critical for external receivers.
- **Dashboard rail UI** (`AppChrome`, `RailSection`, `ControlSliderView`, `LiveControlsTabPage`, `LiveControlRailBlock`, etc.) lives in `Views/Dashboard/DashboardChrome.swift`; **`ViewKit`** keeps shared configuration helpers (`SentenceRow`, `ToggleRowWithInfo`, `SentenceIntervalControl`, `displayLabel`). GPS sentence groups persist expand/collapse via `PersistentDisclosureGroup` (`UserDefaults`).
- Sidebar pages share **`PageChrome`** / **`PageContainer`** (24 pt inset). `DesignToken` owns spacing, system colors, SwiftUI type roles, and content breakpoints; layout types read it. `AppColors` remains the console palette and the tinted status colors of unmigrated pages. The default readable column is 920 pt. Connection and Simulation use `ResponsiveLayout.adaptivePageMaxWidth` (1120) and ordinary width-class stacks. Width class is available page content, not the window: Compact is below 720, Regular is 720 until 900, and Wide is 900 and above. The 960×640 window minimum does not guarantee that content size. Boat and sail rows use a 152/14/280–360 grid and stack below 446. The 320-point library stays local. The toolbar title is the sidebar page name. One shell separator sits under the toolbar. Dashboard, Manual, Diagnostics, and sentence pages are not on these tokens. Dashboard stays full-bleed and does not yet use compact panels.
- **Sentence pages** (Wind / Compass / Hydro / GPS) share **`SentencePage`** in `Views/SentencePanelLayout.swift` (`typealias SentencePanelLayout = SentencePage`). Wide windows are a 50/50 split: stacked sentence cards left (`sentenceCardMaxWidth` 520), live/map right. Use `live:` for titled **Live Data** GroupBoxes (top-aligned with the first sentence card; `--` when not transmitting). GPS uses `preview:` so the map stays in the right half.
- **Toolbar:** one Start/Stop control (⌘R) at `.primaryAction`; Idle/Transmitting + transport + primary output stay at `.status`. Do **not** put ⌘R on a `CommandMenu` — macOS attaches that menu to the toolbar button. Simulation Start/Stop lives in `CommandGroup(after: .sidebar)` with no shortcut.

### Live Controls rail (leading dock) — layout invariants

Do **not** let the scroll area size itself from **intrinsic width** of the active tab. `Slider` rows and `Picker` rows (e.g. Boat) report different ideal widths; if `ScrollView` content only uses `.frame(maxWidth: .infinity)`, the **document width** can still change when switching segments, so the column **appears to resize horizontally**.

- **`AppChrome.liveControlRailOuterWidth`** must stay in sync with the left rail frame in `DashboardView` (single source: `AppChrome.liveControlRailOuterWidth`).
- **`AppChrome.liveControlScrollViewportWidth`** = outer width minus **only** `railPadding` (the scroll column inside the padded panel).
- **`LiveControlsTabPage`** applies horizontal inset **then** **`.frame(width: liveControlScrollViewportWidth)`** so every tab’s body shares one fixed width.
- **`LiveControlRailBlock`** uses a **leading title column** with `.frame(maxWidth: .infinity, alignment: .leading)` and the value on the right so headline/subtitle don’t “jump” when the trailing string length changes.

New live-controls tabs should go through `LiveControlsTabPage` + `LiveControlRailBlock` (or `ControlSliderView`) rather than custom padding stacks.
